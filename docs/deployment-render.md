# Deploying TuneBoxd on Render

TuneBoxd runs on Render as **one Web Service**. The Express backend serves both
the API (`/api/*`) and the built React app, so the browser sees a single origin.
The database stays where it is: **Amazon RDS MySQL** (`us-east-1`).

```
Browser ──HTTPS──▶ Render Web Service (Express: /api + React build) ──TLS, port 3306──▶ AWS RDS MySQL
```

## Why one service (and why there is no CORS config)

The frontend calls the API with relative URLs (`/api/...`) and logs in with an
`HttpOnly`, `SameSite=Lax` cookie. Hosting the frontend and API on the same origin means:

- **No CORS is needed.** The API sends no `Access-Control-Allow-*` headers, so other
  websites can't call it with a visitor's cookie.
- **Session cookies just work.** If the frontend were a separate Render Static Site,
  `tuneboxd.onrender.com` and `tuneboxd-api.onrender.com` would count as *different
  sites* (`onrender.com` is on the Public Suffix List). The cookie would then need
  `SameSite=None`, and browsers that block third-party cookies (Safari, and Chrome in
  some modes) would still log users out.
- It is one free service instead of two.

## What changed in the code

| File | Change |
| ---- | ------ |
| `backend/src/app.js` | Serves `frontend/dist` and sends `index.html` for client-side routes, **only if a build exists**. Adds `GET /api/health`. |
| `backend/src/config.js`, `db.js` | `DB_SSL=true` turns on TLS to RDS with certificate verification (mysql2's bundled Amazon RDS CA). Unset means no change locally. |
| `package.json` (root) | `render-build` (install + build frontend) and `start` scripts. |
| `render.yaml` | Render Blueprint: service settings and env var names. **No secret values.** |

These were already production-ready: `trust proxy` (needed for secure cookies behind
Render's proxy), `Secure` + `HttpOnly` + `SameSite=Lax` cookies when `NODE_ENV=production`,
and refusing to start without `SESSION_SECRET` in production.

Local development is unchanged: `npm run dev` still runs Vite on :5173 with its `/api` proxy.

## Environment variables on Render

| Key | Value | Secret? |
| --- | ----- | ------- |
| `NODE_ENV` | `production` | no |
| `NODE_VERSION` | `22` | no |
| `DB_HOST` | RDS endpoint (`....us-east-1.rds.amazonaws.com`) | **yes** |
| `DB_PORT` | `3306` | no |
| `DB_USER` | DB user | **yes** |
| `DB_PASSWORD` | DB password | **yes** |
| `DB_NAME` | `music_review_app` | no |
| `DB_SSL` | `true` | no |
| `SESSION_SECRET` | generated by Render | **yes** |
| `MUSICBRAINZ_CONTACT` | a team email or the GitHub URL | no |

Do not set `PORT`. Render sets it and the app reads it.

Secrets are entered only in the Render dashboard. They never go in Git, `render.yaml`,
screenshots or the report. The instructor never needs them: they just open the URL.

**Recommended:** create a separate MySQL user for Render that has only the rights the app
needs, instead of reusing the admin/master user:

```sql
CREATE USER 'tuneboxd_app'@'%' IDENTIFIED BY '<long random password>' REQUIRE SSL;
GRANT SELECT, INSERT, UPDATE, DELETE ON music_review_app.* TO 'tuneboxd_app'@'%';
```

(Migrations need more rights. Keep running `npm run migrate` locally with your own user.)

## Network access between Render and RDS

Render connects to RDS over the **public internet**, so the following must be true:

1. **RDS → Connectivity & security → Publicly accessible = Yes.** It already is if you
   can connect from your laptop.
2. **The RDS security group allows inbound MySQL from Render's outbound IPs.**
   - In Render, open the service, click **Connect** (top right), then the **Outbound** tab.
     Copy the IP ranges listed for your region.
   - In AWS: **EC2 → Security Groups**, open the group attached to the RDS instance,
     then **Edit inbound rules → Add rule**: Type *MySQL/Aurora* (TCP 3306),
     Source = *Custom*, paste one Render range. Add one rule per range, with a
     description like `Render tuneboxd`.
   - Keep your team's existing rules for your own IPs.
3. **Do not open 3306 to `0.0.0.0/0`.** Render's ranges are shared by other Render
   customers, so the DB password and TLS are still what protect the database. This is
   another reason to use a strong, least-privilege DB user.
4. The connection is encrypted with `DB_SSL=true`. This was tested against your RDS
   instance and negotiates `TLS_AES_256_GCM_SHA384`.

## Costs and limitations

**Render Free web service: $0.**
- It **spins down after about 15 minutes with no traffic.** The next visit takes roughly
  30–60 seconds to wake up. Before a demo or grading, open the site once to wake it.
- Includes 750 free instance hours per month per workspace, which is enough for one
  service running all month.
- 512 MB RAM and a small CPU share. That is fine for a class project.
- **Sessions live in memory**, so every spin-down, restart or redeploy logs everyone
  out. Accounts and data are safe in MySQL. The log warning `MemoryStore is not designed
  for a production environment` is expected for the same reason.

**Render Starter ($7/month)** removes spin-down, so sessions survive idle periods. They
are still lost on redeploys. Only worth it if spin-down is a problem for grading.
You do **not** need it to share the site.

**AWS (unchanged by this deployment, but good to know):**
- RDS instance and storage cost what they already cost (or are covered by the Free Tier).
- AWS charges about $0.005/hour (~$3.60/month) for each public IPv4 address. A publicly
  accessible RDS instance already has one.
- Data sent from RDS to Render counts as AWS data transfer out. The first 100 GB/month
  are free, and TuneBoxd uses a tiny fraction of that.

**Other limitations:** MusicBrainz allows 1 request per second, so search can feel slow
if several people use it at once. Profile pictures are stored as small data URLs in
MySQL, so there is no file storage to set up.

## Step-by-step: deploying on Render

1. **Push the code** (including `render.yaml`) to the `main` branch on GitHub.
2. Go to <https://dashboard.render.com> and sign up/log in with **GitHub**.
3. Click **New +** → **Blueprint**.
4. **Connect** the TuneBoxd GitHub repository. If it is not listed, click
   *Configure account* and grant Render access to that repo.
5. Render reads `render.yaml` and shows the `tuneboxd` web service (Free plan, Virginia).
   Fill in the prompted secret values: `DB_HOST`, `DB_USER`, `DB_PASSWORD` and
   `MUSICBRAINZ_CONTACT`.
6. Click **Apply** / **Deploy Blueprint**. The first build takes a few minutes.
7. **The first deploy will probably fail at "Unable to connect to database (ETIMEDOUT)".**
   That is expected, because RDS doesn't allow Render yet. Open the service →
   **Connect** → **Outbound**, copy the IP ranges, and add them to the RDS security group
   (see *Network access* above).
8. In Render, click **Manual Deploy** → **Deploy latest commit** (or **Restart service**).
9. In **Logs**, wait for `Database connection successful.` and then `TuneBoxd API listening ...`.
   The service status turns **Live**.
10. Open the URL at the top of the page (`https://tuneboxd.onrender.com`, or similar if
    the name is taken) and share it with your instructor.

## What to test after deploying

On the live `https://...onrender.com` URL, preferably in a private/incognito window:

1. `https://<your-url>/api/health` returns `{"ok":true}`.
2. The home page loads. **Refresh on a deep link** such as `/community` or `/diary`: it
   should load the app, not "Not Found".
3. **Register** a new account, then **log in**. You land on Profile.
4. **Refresh**: you stay logged in. In DevTools → Application → Cookies, `tuneboxd.sid`
   shows **HttpOnly ✓, Secure ✓, SameSite Lax**.
5. `/api/me` while logged in shows your user, and after **Logout** it returns 401.
   Visiting `/profile` after logout redirects to Login.
6. **Search** "in rainbows", open the album, **write a review**, **add a diary entry**,
   and **comment** on a review.
7. In MySQL Workbench, confirm the new user, review and diary rows are in
   `music_review_app` on RDS.
8. **Edit profile** with a photo (checks the larger upload limit).
9. Test on a phone or a second browser, logged in as a different user (follow, comment).
10. Wait more than 15 minutes, then reload. It wakes up slowly, then works (you'll need to log in again).
11. **Render → Logs**: no errors apart from the expected MemoryStore warning, and no
    credentials are ever printed.

## Troubleshooting

| Symptom in Render logs | Fix |
| ---------------------- | --- |
| `Unable to connect to database (ETIMEDOUT)` | Render's outbound IPs aren't in the RDS security group, or RDS isn't publicly accessible. |
| `ER_ACCESS_DENIED_ERROR` | Wrong `DB_USER`/`DB_PASSWORD`, or the user has `REQUIRE SSL` while `DB_SSL` isn't `true`. |
| `ENOTFOUND` | `DB_HOST` has a typo, `https://`, or a `:3306` suffix. Use the bare hostname. |
| `SESSION_SECRET must be set in production.` | Add `SESSION_SECRET`. |
| Build fails at `vite: not found` | The build command must be `npm run render-build`, which installs the frontend dev dependencies. |
| Logged out right after logging in | The site is being opened over `http://` instead of `https://`. |
